## Template contract

State-local `templates.json` is versioned JSON with a built-in immutable `default` template, user copies, and per-project-code assignment. Missing file returns the default in memory without migration writes. Validated atomic replacement uses existing per-state lock; malformed/unsupported JSON is surfaced and never silently reset. Assignment is by case-insensitive discovered project code; existing discovery grammar remains unchanged. Unknown template references fail clearly, deletion of assigned templates is blocked. Normal/demo state are separate.

Each template has id/name, production directory (default `3_制作`), asset root (`1_设定`), asset categories (default 角色/场景/道具), final directory (`4_交付`), keep-name routes (剧本→2_剧本分镜, 甲方→0_甲方, 参考→_参考), and test directory (`_测试`). These are safe relative paths inside the discovered project, not absolute paths. Additional asset categories are allowed. Default naming uses the existing naming implementation unchanged. Optional per-mode file naming patterns override it for `shot`, `asset`, `final`; tokens are finite and documented: `{original}`, `{stem}`, `{ext}`, `{prefix}`, `{note}`, `{date}`, `{date_long}`, `{period}`, `{episode}`, `{scene}`, `{shot}`, `{sequence}`, `{resolution}`. No Python formatting/access/evaluation; unknown tokens rejected. `ext` includes the dot, `date` YYMMDD, `date_long` YYYYMMDD, `period` AM/PM, absent optional values empty. Sequence is an integer decimal, allocated collision-free using the existing occupied-name model. Custom pattern outputs must be a single valid Windows component; no paths, device names, traversal, invalid characters or overwrite. Directory sources keep their names. Existing default merged-shot and media-width rules stay unchanged. Custom patterns can use numbering but need not mimic legacy inference. Edit applies to future plans only; execution rejects a stale template revision rather than silently changing a displayed destination.

## Rule definition and matching

State-local `automation-rules.json`, schema version 1. Rule fields: stable id, name, enabled (new/copied/imported rules false), ordered list priority, optional watch-root scope (empty = configured watch roots), condition tree, ordered actions. No arbitrary code. JSON import validates the entire document before mutation, uses new IDs and disabled states; export contains definitions only, not run history. Duplicate creates a disabled independent copy. Bounded editing: at most 4 group levels, 100 predicates and 20 actions per rule; UI shows limits clearly. Rules list itself is not silently truncated.

Conditions: group `all`, `any`, `none` (none means no child matches), and leaf fields kind (file/folder/image/video/audio/document/other), extension, name, size_bytes, created, modified, first_seen_age_seconds, stable_age_seconds. Text operators equals/contains/starts_with/ends_with/glob; extension comparison ignores case and accepts a leading dot. Numeric/date comparisons eq/lt/le/gt/ge; date values ISO8601 with explicit timezone. Age compares nonnegative seconds to a captured aware clock. Text matching is case-insensitive (Windows expectations), literal unless glob. No regex in this release. Folder size is sum of regular tree bytes; type and extension retain directory distinctions. Missing facts never pass comparisons, and explanation says unavailable. Observation ages initialize at first automatic observation, reset stable age on fingerprint change, and use persisted state. Manual preview before observation shows age as unavailable, not zero-age success. Stable age also respects future or recently changed source timestamps.

Automatic rules scan only top-level entries in configured watched roots. Existing hidden/temp/reparse/active-file guards and pause semantics apply. First enabled matching rule claims the item; later rules and legacy inbox fallback do not run for that item, including when its run is already recorded or failed. If none match, legacy behavior remains. Explicit rule scope must refer to configured watch roots; editing rules never adds watch roots. Manual preview can evaluate selected files and selected disabled rules for testing; explicit execution is a separate action and never follows a checkbox or preview automatically.

## Ordered actions and preview

Actions: rename (single-component pattern), move (absolute destination folder chosen explicitly), copy (same), subfolder (safe relative subfolder of current subject parent), project_route (existing project command through the selected template). Directory actions support existing engine tree guarantees. Actions are ordered; after copy the subject becomes the copied item, as with move/rename. Subfolder means move the subject into that folder. Project-route is terminal, allowing existing multiple target planning; it performs copy/move operations without generic-rule implicit duplicate recycling. No action overwrites or permanently deletes. All paths reject reparse points/state overlap/source containment hazards using existing guards. Existing absolute move/copy directories can be chosen outside sync; a destination cannot overlap application state or another selected source. A no-op rename/move is rejected with an explanation, not marked successful.

Preview is read-only for source/destination data and shows every condition result, first matching rule, ordered source→destination steps, collisions, and errors. It reserves planned target names across selected inputs. Execution binds source fingerprint, rules/template revision, and exact planned targets; if definitions/source/occupied destinations changed it fails with a re-preview message, not silent relocation. Sequential execution captures the new subject fingerprint after each committed action, and later actions stop on any failure. All operations go through OperationEngine, with one journal batch per rule run so history/undo remains available. Do not bypass guards or replace the transaction engine. Chain undo needs explicit tests for copy→rename/move, move→rename, and partial failure; extend engine lineage only if tests expose a required narrow change.

## Durable execution and background integration

A separate automation SQLite ledger stores observations and run state, under the same process lock/worker. Claim the rule revision + original identity/content fingerprint before the first mutation, with durable running status. Record action progress and batch ID. Successful runs are suppressed across restart for original and surviving output identity/fingerprints; unchanged copy sources do not copy forever. A running record after interruption or partial/failed run does not silently rerun; preview explains review required and shows history. A changed source or edited rule creates a new eligible version; undo does not automatically re-trigger the same run. Manual retry is intentionally conservative: inspect history, correct/edit the definition or source, and preview again; no unsafe blanket reset button. Rule revision uses content digest, not position or enabled state; enabling/disabling/reordering alone must not cause duplicates.

Scheduler integrates matching before legacy inbox fallback but introduces no new timer. New rules are disabled by default and need explicit enable plus existing unpause. The shared Coordinator runs all template/rule load/save/preview/execute/scan I/O. Same-value/history edits, rule/template changes, new selection, demo switch and service replacement invalidate in-flight previews; UI updates from old states are discarded. Rule histories identify rule name and step outcomes alongside existing operation history.
